# Working in this repository

- Start with `src/`, `scripts/`, and the relevant test file. Use scoped `rg` searches. Avoid recursive root-directory scans: `.test-results/` contains large game copies and historical logs, and `dist/` contains prior deliveries.
- Current entry points: `src/HollowConnect/CoopRuntime.cs`, its `EmergencyBenchRecovery.cs` partial, `ResourceShareService.cs`, `BossTravel.cs`; network/entity code is in `src/HKMP/`; shared models are in `src/HollowConnect.Core/`.
- Use `scripts/Build.ps1` for incremental production builds. It does not run tests or package. References are prepared only when missing or when `-RefreshReferences` is explicit.
- Select `-Target Core`, `Smoke`, or `Installer` to build that tool. `-RunTests` executes core tests; `-TestSelection <file>` executes an explicit list. See `docs/DEVELOPMENT.md`.
- Respect the user's test scope. Normal changes use the agreed recent/related checks and directly affected specialties; do not automatically run all Unity suites for a small change, version bump, or packaging request. Major protocol/lifecycle changes or an explicit full-test request warrant the full matrix.
- Build Smoke once per suite. `Run-Two.ps1 -NoBuild` reuses that prepared output and checks production dependency hashes. Rebuild after editing source; do not mix older Smoke output with new production DLLs.
- Preserve historical evidence, failures, delivered ZIPs, private saves, and game assemblies. Consult only the report relevant to the current issue. Test inventory: `docs/TEST-INVENTORY-2026-10-18.md`; current update: `docs/UPDATE-0.1.26.md`.
- Run actual game checks only in the existing isolated game copies. Keep test plugins out of deliveries and do not modify personal saves. Record the tested binaries; version changes do not retrospectively certify new hashes.
- Packaging is explicit via `scripts/Package.ps1`; normal package generation hashes only new/missing ZIP entries. `-RebuildChecksums` is an explicit maintenance operation for all historical ZIPs. Package integrity checks and game/regression runs are separate operations.

## Iteration speed and long test runs

- Use staged validation: incremental build and related core checks first, the smallest game reproduction second, then required regression coverage on stable production binaries. Fix a failed early stage before starting the slow matrix. Documentation/rule-only changes use text/diff checks; do not build or launch games.
- Before a run likely to exceed 10 minutes or eight dual-client cases, write an explicit case list, why each group is needed, reusable results, and a rough duration from relevant prior runs when available. Tell the user the scope and expected long portion, then proceed within existing authorization; do not turn this into another approval request.
- Do not interpret “full matrix” as every Unity/Boss suite. Major protocol/lifecycle changes require the 12-case room matrix plus directly affected specialties, unless the user specifies another scope. Add other suites only for an actual dependency, failure, unresolved concern, or explicit request; record that reason.
- Share the first useful milestone as soon as the build and direct checks pass: give the local build path, verified scope, and pending checks. Continue required work in the same task. Do not wait for every slow suite to provide a usable progress result, and do not package/install/publish just to produce that milestone.
- Keep a durable run selection and per-case status/evidence under one task-specific analysis directory. Use a script to own game startup, bounded waits, logs, timeouts, and path-checked cleanup. Prefer a supported durable runner; if unavailable, run small resumable batches. Do not make a long suite depend on a single live tool session or manually launch each next case after every poll.
- Resume from evidence after interruption: check the recorded runner/PIDs and current case before launching anything. Reuse completed cases whose production hashes, relevant test logic, options, game dependencies and isolation setup still match, and whose two endpoints and strict logs passed. Run only missing, interrupted, failed or invalidated cases in new directories. Never restart an entire suite solely because the tool session was lost.
- Freeze production binaries for final regression. Rebuild Smoke only when its inputs change and use `-NoBuild` across prepared suites. A test-only fix invalidates affected cases, not all otherwise valid production-hash results; record the test change and rerun its dependent cases. Changed production DLLs require fresh final-hash evidence for the required scope; keep earlier results as development evidence.
- Preflight new or changed slow fixtures before the matrix: validate native scene/additive-scene ownership, required objects/FSMs, authority, and entry conditions in the smallest applicable run. Include useful names/states in failures. Do not bypass native progression to make a fixture pass.
- On failure, stop that dependent batch, classify product/fixture/environment failure, and fix the cause before retrying. Allow at most one unchanged retry when evidence supports a transient failure; retain both attempts. Do not repeatedly rerun slow passing groups while investigating an unrelated failure.
- Independent reads/build preparation may run concurrently. Game suites sharing `game-host`/`game-guest` must remain sequential because launchers replace files and stop those processes. Never claim parallel testing without independently isolated game copies; do not create more copies or agents merely to satisfy a speed target.
- Let runner scripts monitor cases internally. At progress checkpoints read compact status and new failures; open detailed logs only for a failure or stalled boundary. Avoid repeated whole-log reads and updates that only say the same test is still running. Record passed/pending/failed counts and materially new findings in updates.
- Follow the concrete workflow and evidence rules in `docs/DEVELOPMENT.md`. These rules govern test scheduling and reuse; they do not imply an automatic resume/cache feature exists in every current runner.
