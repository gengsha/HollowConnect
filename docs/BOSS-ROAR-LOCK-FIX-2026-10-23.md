# 收藏家与普通格林战吼永久锁定修复

用户报告：五门收藏家开场时，一人利用原版菜单技巧跳过战吼，其他人永久僵直；普通格林敬礼受击后的愤怒战吼也曾随机锁住部分玩家，不能操作、传送或受伤。

## 已确认的原因与证据边界

原生 `Knight/Roar Lock` 在 `ROAR ENTER` 后进入 `Lock Grounded` 或 `Lock Air`，调用 `RelinquishControl` 并停止动画控制。`ROAR EXIT` 通过原生 `Regain Control` 状态恢复操作和动画。收藏家开场约 4.25 秒，普通格林敬礼受击后的战吼约 1.5 秒，都向各自的 Hero 引用发送这对事件。

旧实现逐条重放 Boss 的可靠 FSM 动作。可靠数据会去重并补发，但动作本身允许迟到；快照字段有新旧过滤，动作事件仍被保留。因此“结束”先到、“开始”后到时，Boss 已继续攻击，接收者却重新进入战吼锁定，后面没有新的退出事件。

`.test-results/roar-baseline-grimm-delay` 在修复前的固定生产 DLL 上实际复现此问题：普通格林原生敬礼受击后，将副本的 `ROAR ENTER` 留到 `ROAR EXIT` 之后再执行，副本恢复控制断言失败。权威使用原生 `No Roar` 标记免于锁定，且仍能正常受伤。这是对菜单跳过控制结果的隔离注入，没有自动执行原版卡菜单技巧；没有用户原始网络日志，不能证明用户当时的包序完全相同。

| 原生流程 | 风险结论 | 最小验证 |
|---|---|---|
| 五门 `GG_Collector_V` 的 `Control/Roar → Music → Roar End` | 开始、结束动作乱序可留下个人控制锁 | 原生五门序列索引 26 的上下文，分别验证正常、开始迟到、结束事件缺失 |
| 普通格林 `GG Bow Wait` 受击后 `Roar Antic → Roar → Roar End` | 同一事件重放风险 | 实际骨钉伤害触发原生愤怒战吼，交换主客权威 |
| 动态 `Roar Wave Emitter` | 本轮未发现其表现终止是控制锁定的必要条件 | 保留原生发射、表现和 `END` 流程；不以波纹消失代替控制验证 |
| 其他 Boss 的战吼、碰撞触发战吼和过场 | 未在本轮验收 | 未扩大到其他 Boss；需要各自原生流程证据 |

## 实现

`BossRoarLock` 仅为收藏家和普通格林识别原生零延迟的开始／结束动作，并在对应的主、副 FSM 上追加当前战吼布尔值。权威执行原生动作后立即发布该值，复用现有可靠 FSM 布尔快照和逐字段版本过滤；迟到的旧值无法覆盖较新的结束值。

副本根据当前值执行自己的原生 `ROAR ENTER`／`ROAR EXIT`，忽略这两个旧式独立动作的重放。晚入场读取当前值，原生阶段中断或对象关闭会清除已取得的锁。只释放本次实际取得、仍在 `Lock Grounded`／`Lock Air` 的个人战吼 FSM，不直接强行调用全局恢复控制。旧结束动作也不能解除后续另一段原生战吼。

代码入口：`src/HKMP/Game/Client/Entity/BossRoarLock.cs`，集成于 `Entity.cs` 的动作观察、可靠布尔发布、快照应用和清理；独立事件拦截位于 `LocalBarrierEvents.cs`。没有新增网络包种类。

验证计划及逐项状态位于 `.analysis/boss-roar-lock-20261023/`：`cases.json`、`validation-plan.md`、`*.status.json`。每组记录生产哈希、Smoke 哈希、角色顺序、运行器／游戏 PID、双端日志和严格日志结果。使用真实 Unity 双客户端、本机 UDP、内存角色，禁止写存档和模组全局设置；未安装或打包。

11 项相关核心检查已通过，覆盖逐变量布尔快照乱序／补发／序号回绕、可靠事件保留、快照所有权、密集动作批次、原生结算与权威交接数据。`ReliabilityProbe.ReorderedSnapshots` 新增“旧 true 不能覆盖新 false，同时保留未被新包覆盖的其他布尔字段”的断言。
