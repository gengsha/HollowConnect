# 梦境击败记录与个人精华补齐

本轮延续失落近亲尸体结算修复，处理共享永久进度开启时，一次性梦境击败记录漏记后仍可入梦、未领取灵魂不出现的问题。不升版本、不打包、不安装，不读取或修改个人存档。

## 已确认问题与实现

- `ProgressCatalog` 原有失败冠军记录，缺少失落近亲与灵魂暴君的 `infectedKnightDreamDefeated`、`mageLordDreamDefeated`。补上这两个正向布尔后，已有队友或房间并集记录可以在加入／重连时修复漏记；关闭共享不会接受它们。
- 只补 PlayerData 仍不足：`.test-results/dream-20261023-kin-catchup1` 的客机已在 `Abyss_19`，真实 UDP 入队核对后击败字段为 true，但 `IK Remains/Control` 仍在 `Glow`，未领取灵魂仍隐藏。
- 新增 `DreamVictoryProgress.Refresh`，在共享进度实际应用后，仅对三个一次性梦境的原生返回房间重新检查静止的入口 `Glow → Check`。未领取时，只启用尚未运行、且原生 `Init` 同时检查本次击败和个人领奖标记的灵魂 NPC。原生对话、精华发放、领奖标记和控制恢复继续自行执行。
- 三种一次性梦境的共享提示显示 Boss 中文名，不再将内部 PlayerData 字段显示给玩家。
- 精华余额、所有 `*OrbsCollected`、白色防御者／灰色王子的击败次数与可重复挑战状态不进入共享并集。本轮预检证明后两者的原生个人次数、死亡与返回可以正常推进，没有据静态猜测新增尸体／计数网络重放。

补齐需要队友或房间保存的并集中至少存在一份有效击败记录；不会从精华余额推算历史，也不会自动给每个人直接加精华。

## 验证方法与边界

选择与原因在 `.analysis/dream-settlement-20261023/selection.json`，后台执行与每项状态在同目录。使用既有 `game-host`／`game-guest` 串行运行，同机真实 UDP，Smoke 阻止个人存档写入。实际入梦前的场景准备不认证真实梦之钉进入；战斗激活、阶段、尸体、梦境返回、起身与领奖均验证原生流程。没有认证跨机器 FRP、所有 Boss 或房间矩阵。

旧档补齐用例在接收方进入并停留于原生入口房间后，才允许已有完成记录的来源客户端连接。核对入口关闭、未领取者原生领奖、已领取来源不重复领奖，再退出并重新进房确认奖励不重生。

开发阶段保留以下证据：

- `kin-catchup1`：产品问题；补共享字段后已加载入口与奖励仍不刷新。
- `kin-catchup2`：夹具错误；误把 remains 对象本身必须 inactive 作为判据。原版关闭的是其 `Dream Enter`，正确判据为 `Control=Off` 且该子对象 inactive。
- `kin-catchup3`：开发构建通过，含原生 400 精华、已领奖来源和重进房去重。
- 暴君、白防、灰王子的预检，以及触发区／合法睡眠前置调整，均保留在本任务目录；它们是开发证据，不自动认证最终生产哈希。
- `final1` 前四组补齐用例通过；随后发现运行器用 `Environment.SetEnvironmentVariable(name, null)` 在当前运行时留下空值，而 Unity 将空值视为非 null 模式开关，后续选择误跑为补齐用例。已标记这些后续结果无效，改用 `Remove-Item Env:`，记录实际模式变量，并核对双端最终场景标记。
- `final2` 的暴君完整两阶段结算、白防与灰王子的首次／重复组合通过。补充中文提示后生产哈希改变，以上结果均保留为开发证据，`final3` 对选定九组统一使用最终哈希重新验收。
- `final3` 的失败冠军用例停在 `Dormant` 后超时：本任务运行器遗漏既有 `Run-Dream-Variants -LifecycleCheck` 同时开启的 `DREAM_VARIANT_DAMAGE` 原生入场预检。修正参数后仅以 `final4` 补跑失败冠军；不改生产 DLL、Smoke 或其它八组逻辑，不重跑通过项。
