# 格林帐篷无法操作反馈排查（2026-10-25）

反馈为三人在普通格林帐篷无法操作，只有截图，没有版本、日志、任务轮次或网络过程。当前受测构建的四组双端流程均未复现，具体原因仍未知。本轮没有修改格林战斗、演出或控制恢复代码。

| 实际检查 | 结果 |
|---|---|
| 第二轮交火、双方首次战斗出场 | 双方越过原生对话与格林之子吸收流程，格林激活，控制恢复 |
| 一方首次出场、一方已进入重战分支，guest 先入成为场景权威 | 双方正常进入战斗并恢复控制 |
| 双方重战 | 双方正常进入战斗并恢复控制 |
| 原生敬礼时受击触发愤怒战吼 | 双方实际进入战吼锁，再经原生恢复状态回到 `Detect` |

两端均要求原生剧情抵达 `Battle Start`，本地 Boss 表示激活，输入可用、没有 relinquished 控制锁、暂停可用，且战吼 FSM 在 `Detect` 持续至少三秒；严格日志均通过。原生资格仅在内存夹具初始化，实际加载、触发、对话、吸收及受击反应走原生路径，没有强制设置 FSM 为成功状态。

旧版确有战吼开始／结束事件乱序造成永久个人控制锁的问题，已在此前修复，见[战吼修复记录](BOSS-ROAR-LOCK-FIX-2026-10-23.md)。截图悬空姿势与该表现相容，但不知道反馈者版本，不能据此认定原因。原生出场还有等落地、等格林之子 `ABSORB END` 的阶段；本轮均自然通过，没有证据证明该反馈卡在这些等待上。两端均实际加载 `Grimm_Main_Tent_boss`，未观察到本轮附加场景缺失。

本轮使用既有两份隔离游戏、本机 UDP，禁止保存内存测试档；不代表三人实机、异机互联网、演出中断／晚入／权威退出或完整击杀流程已通过。受测版本为升版前固定生产 DLL，各哈希和逐端结果记录在[机器证据](evidence/grimm-tent-audit-2026-10-25.json)，不追认为 0.1.38 升版后的实机证据。

含现有紧急回椅功能的版本可用 `Ctrl+Alt+F12` 断开联机并返回德特茅斯长椅；这是脱离手段，不能确定卡死原因。`F9` 打开只读诊断面板，另点“导出诊断”才写出报告。
