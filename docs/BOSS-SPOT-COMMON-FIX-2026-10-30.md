# Boss 抽查与公共结束流程修复（2026-10-30）

本轮按用户要求停止旧版本比较，继续修正“首领已死亡，但部分参与者不能离开”的公共流程。此前公共机制及开发证据见 `BOSS-FLOW-COMMON-RECOVERY-2026-10-30.md`；该报告的旧 DLL 哈希不能替代本轮构建的验收。

## 真实复现与修复

抽查了水晶守卫、残破容器、Nosk。使用现有两份隔离游戏、全新未保存角色、真实 UDP 联机，第一人触发原生开场后第二人进场。测试先证明首领能受到普通骨钉伤害，再调用原生伤害完成击杀，等待原生尸体和门禁流程，最后用真实移动输入穿过出口。测试不直接设置战斗 FSM 状态、不伪造完成事件，也不强制开门。

| 确认问题 | 原生证据 | 公共修复 |
| --- | --- | --- |
| Nosk 后进入者的本地控制器未启动 | `boss-spot-20261030-nosk-b`：后来者 `Battle Scene` 留在 `Init`，首入者正常离开 | 开战回执支持原生广播；通过首领 HealthManager 的 `sendKilledTo` 关联验证本地控制器及 `KILLED → BOSS DEATH → FINISHED → BG OPEN` 结构 |
| 休眠原生对象尚未运行 `HealthManager.Start` | `boss-spot-20261030-nosk-fixed-j`：开战回执为真，但后来者原生 `sendKilledTo` 为空 | 依照原生序列化的 `sendKilledToName`／`sendKilledToObject` 在当前主／附加房间内解析唯一、本地的目标，并补齐两份 HealthManager 的缺失引用；不唤醒休眠 AI |
| 原生对象池清掉死亡标记，真实死亡被联机层当成阶段事件 | `boss-spot-20261030-nosk-fixed-m`：首入者确实发送 `KILLED` 并产生尸体，但 `Die` 返回后 `isDead=false`；后来者收到的是特殊死亡，未执行完整死亡 | 在原生 `Die` 调用期间观察其真实 `OnDeath` 回调；回收后的标记不能否定已发生的完整死亡。原有 `hasSpecialDeath`／`deathReset` 阶段保护继续生效 |
| 残破容器的个人感染出口未收到尸体事件 | `boss-spot-20261030-vessel-private-c`：首入者的 `infected_door` 进入 `Burst`，后来者留在 `Idle`；共享进度对照通过 | 将已登记尸体接入公共终态处理；结构验证接收方具有原生击败标记判断，且事件沿原生后续流程移除自身实体碰撞，不依赖 `IK GATE OPEN` 的字面特例 |

水晶守卫原构建未复现此故障，仍在最终构建上检查尸体逃离、长凳恢复与两个真实门洞。其后来者入口保持本地行为，不能用远端开场事件强行关闭原本开放的门。

原生程序集只读审计沿用 `hollow-knight-boss-net-audit` 风险模型。HealthManager 的目标初始化、普通死亡末尾回调，以及 EnemyDeathEffects 回收前调用 `SetIsDead(false)` 的 IL 保存于 `.analysis/boss-spot-20261030/native-death-and-target-il.txt`。这部分证据来自实际隔离副本的程序集。

## 机制边界

开战回执复用现有带版本的 FSM 布尔快照，等待本地控制器就绪后消费一次。完成回执继续复用击败记录、原生终态快照和本地门禁处理。识别结构只读取状态图；执行仍由原生动作、计时、尸体、敌人数与多阶段流程负责。

个人世界仍隔离普通远端机关、入口关门和不相关事件。房间访问与战斗轮次校验、重复回执保护、对象缺失时的最终快照恢复均保留。没有新增消息类型或包字段，没有改写权威选举／房间轮次协议。双方应使用同一构建。

开发失败保留：`fixed-k` 说明补齐开战与引用仍不足以修复池化死亡；`fixed-l` 的新增诊断误用 Unity 对象的空条件访问，导致诊断本身在对象销毁后抛错，已修正测试并保留记录，不算产品验收。`fixed-m` 的残破容器通过仅是开发证据，最终使用下列固定生产哈希重验。
