# 公共战斗同步减负与剩余风险

用户授权：在普通流程测试到之前处理已发现的公共性能隐患。此次只改项目与隔离副本，未打包、安装或修改日常游戏及存档。

## 改动与边界

| 已确认机制 | 本轮处理 | 仍有的边界 |
|---|---|---|
| 子节点持续变化带动整实体可靠 CombatState | `2cde6bd` 对至少 512 字节、确实能缩小的完整快照使用独立 Deflate；小包保留原编码 | 仍完整采样、完整发送；没有改成依赖前包的增量 |
| 每次数字/布尔编码分配临时数组；未变化状态也新建包和 ToArray | `2cde6bd` 直接写标量位，复用尚未发布的采样缓冲，比较后才冻结/压缩 | 20 Hz 原生状态读取、字符串编码和周期层级刷新仍有开销；不能称零分配 |
| 主线程每帧复制并一次执行全部积压回调 | `d197660` 按 FIFO 处理，约 2 ms 后在完整回调之间让出下一帧，同时消除逐帧队列复制 | 单个回调可以超过预算；没有丢弃消息、拆开一个数据报或改变断线代际检查 |
| 敌人位置平滑被编译开关关闭 | 保持待验证，未直接启用旧的固定 1/60 秒协程 | 网络不佳时仍可能跳动；需要一起验证显示位置、子命中盒、传送与接管 |
| 预制体缺失/歧义时重复全局资源扫描，精确来源成功仍先遍历全部 FSM | `bfae77a` 精确来源失败才遍历；同帧共用资源候选，次帧重查，离场/断线清理 | 缺失仍失败，唯一原生资源规则不变；瞬间大量 Instantiate/副本构造的固有成本尚未消除 |

完整快照顺序仍由原来的组件级历史过滤处理，服务器仍保存最后一份完整状态。压缩包只新增外层标记和未压缩长度；解码限制输出长度，再沿用原节点、路径、数字和组件上限。没有改变 FSM 行为、伤害、攻击频率或重试期限。后续交付要求双方使用同一个新完整包，旧客户端不能读取新增压缩载荷。

## 同配置实际攻击对比

两个目录均为 `Mines_11,Ruins1_30`、真实 `right1`、近距离免伤靶子、每房 35 秒、同一组性能钩子；观察到原生 CrystalCrawler/Beam 和 Mage Orb 生成。它们是同机 UDP 批处理观察，不是实机渲染帧率或 FRP 带宽测试。

| 接收端 CombatState 应用层载荷 | 当前逻辑基线 | 压缩候选 | 下降 |
|---|---:|---:|---:|
| Mines_11 整房 | 7,526,856 字节 / 3,372 次 | 2,171,721 字节 / 3,330 次 | 约 71% |
| Ruins1_30 整房 | 1,750,433 字节 / 1,380 次 | 625,965 字节 / 1,340 次 | 约 64% |

基线为 `.test-results/combat-alloc-baseline-20261015-a`，HKMP SHA256 `6F5C2BFE905D915DE5F26752E581B2E7B774EB97D386539CCBBDDA9C590B03B8`；原 DLL 另存为该目录的 `HKMP.baseline.dll`。候选为 `.test-results/combat-alloc-compressed-20261015-a`，HKMP SHA256 `1058DD3BAE5BC4CCB2D98863B3881AAA033DB6B5A604A0F6DF5007D7CF7620E4`，此时还不含后续队列/资源优化。不能把这两个旧哈希的对比当作最终构建的全部验收。

CPU 有取舍：同配置基线/压缩候选的采样累计分别为水晶房 629.8/726.8 ms，圣所 895.2/607.9 ms；接收应用分别为 295.8/432.9 ms、101.7/133.6 ms。压缩减少网络负担，同时增加接收解压开销，并非每条路径的 CPU 都下降。这些是整段累计量，不是单帧耗时。Unity Mono 没有当前线程分配计数器，探针明确输出 unavailable，不能将 allocatedBytes=0 当作零分配证据。

## 最终构建验证

生产构建提交：`bfae77a403b4b4959098c6056b926d6337829c87`，三个 DLL 的 ProductVersion 均带此提交。147 项自动回归、14 项严格日志门槛通过。新覆盖包含全部标量旧线格式与浮点位、独立完整压缩/长度拒绝、采样缓冲所有权，以及积压回调预算/FIFO/下一帧语义。

| 最终目录 | 配置与结果 |
|---|---|
| `.test-results/combat-performance-final-host-20261015` | 房主先入，两房实际攻击、双方嵌套命中盒/旋转/透明度/材质及真实 HeroBox 受伤；完整快照乱序、重传、回绕、缓存副本和接管夹具通过 |
| `.test-results/combat-performance-final-guest-faults-20261015` | 副机先入并成为场景权威；相同检查及实际攻击通过；固定种子丢包、重复、乱序均实际发生，双方 nestedResends=0；后来者在两房分别记录到 9、25 份压缩初始房间快照 |

两组均验证真实 Unity 上六个耗时回调按 FIFO 分六帧完成，以及十二个不同资源缺失请求同帧复用、次帧重查、scope 清理。完整快照顺序/缓存/MakeHost 是使用未连接发送器的真实 Unity 夹具，不冒称一次真实 UDP 断线接管；初始房间快照和嵌套命中盒/受伤检查另走实际房间网络。

故障注入的房主端记录丢弃/乱序/重复为 2,220/1,389/630，副机端为 740/463/210。两组最终目录均有双方 done、shutdown-offline 及 shutdown-server-stopped；停止经精确路径核对的隔离进程后，重新严格扫描全部五组日志并核对测试目录、两份游戏副本与最终两组的三个 DLL 哈希一致。测试插件已重命名停用，无剩余游戏进程；见 [停机后核验](evidence/combat-performance-2026-10-15.json)。

最终两组含约 4 秒伤害夹具，累计 profile 的观察范围比上表纯攻击对比更长，不能直接以总字节比较。首次性能夹具构建缺少 PacketManager 命名空间，编译失败、没有启动游戏；修正后候选目录 `.test-results/combat-performance-candidate-20261015-b` 保留，不混作最终哈希验收。

真实双机 FRP 的掉帧/延迟改善、全部泪水之城房间、敌人位置平滑和大批副本同时创建仍未验收。地图购买后持续互相不可见、Mines_11 String 数组越界、历史接管飞针与假骑士样本没有由本轮关闭。仍 `releaseReady=false`，已交付包仍为 0.1.15。后续只改测试观测/文档时不重建已验收的生产 DLL。
