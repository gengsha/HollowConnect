# 遭遇战迟入卡门：补齐本地死亡结算（2026-10-22）

本轮处理“另一人先打，后来者进入遭遇战被关住”的通用结算路径。用户没有指定具体房间，以双蘑菇巨怪 `Fungus2_05` 直接检查，继续保留各端原生触发、原生波次、奖励和开门。

## 发现与修复

普通“先打完、另一端再进房”的当前基线双端通过；已有早期死亡计数补偿仍然有效，不能把该基线说成再次复现了全部问题。新增接收边界探针则明确复现了一个遗漏：权威端较早的 Health 快照尚没有 `battleScene`，本机已有的原生战斗引用却被清空，还可能导入权威端的 `notifiedBattleScene=true`。后续死亡不再减少本机遭遇战计数，后来者触发原生关门后便缺少结算来源。

- `HealthManagerComponent.ApplyPhase` 保留已建立的本地原生战斗引用；未解析到战斗对象时，不导入对方的死亡通知回执。已解析的网络控制器仍采用已有快照规则。
- 收到终结死亡时若战斗绑定尚未建立，按实体和原生 HealthManager 记录待处理死亡。原生 `SetBattleScene` 或接收绑定完成后，只补一次缺失的本地计数通知，不重播死亡、掉落或奖励。
- 早到死亡由下一次正数 `Battle Enemies` 初始化消费，补齐波次之间的顺序；已消费记录不会再次用于下一波。
- 明确生命重置取消旧死亡记录，包括接管后的原生生命重置；场景卸载、注销清理记录。竞技场等已网络化控制器不走本地计数补偿。

实现没有新增网络字段、没有按“房间里暂时看不到敌人”强制开门，也不把阶段死亡作为终结死亡。收藏家最终事件开门的修复保留不变。

## 本轮验证

| 检查 | 范围 |
| --- | --- |
| 接收与动作边界、原生双蘑菇战 | 空绑定包保留本机引用；重复死亡；迟到与零值复活包；死亡早于绑定；重复绑定；绑定晚于计数初始化；波次间死亡；复活取消待处理死亡。随后双方完成真实原生结算、领取护符槽并实际走过两扇门。 |
| `late-host` | 房主先打完两只巨怪，访客才进入场景、触碰本机战斗触发器，双方结算、领奖和过门。 |
| `outside-guest` | 访客权威开战并击杀；房主先在同场景触发器外等待，死亡已到达后才触发本地战斗。 |
| `partial-guest` | 访客先击杀一只；后来者入场时必须恰好剩一只，随后继续原生击杀和结算，防止提前开门。 |
