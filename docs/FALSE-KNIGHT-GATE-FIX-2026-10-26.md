# 假骑士多人战后铁门修复（2026-10-26）

报告场景为 0.1.39 三人联机，全员未死亡，战后其中一名非房主被铁门挡住。此次补齐每名玩家自己的原生终局流程，并修复多个接收端共用可变 Boss 状态的问题。两人与三人使用相同处理，不按队友序号或人数特判。

## 原因与改动

1. **各接收端发送队列原先共用可变 FSM 数据。** 一个接收端的后续合并可能改写另一端已经取出、准备编码的批次。`ServerUpdateManager.AddEntityHostFsmData` 现为每个队列复制字典、状态及可变向量；`SnapshotPayload.Copy` 保持快照拥有自己的数据。实际生产队列测试覆盖 1、2、3 个接收者，包括取包后另一端合并、调用者继续修改原数据、后续入队合并。
2. **假骑士不通过已有的 Boss 开门事件路径结算。** 它在最终 `Decrement Battle Enemies → Cough` 阶段修改本地战斗计数。现依据准确 Boss 类型、主／附加场景及原生动作结构，为每个本地场景访问、轮次、实体只记一次终局扣减；动作与快照均可提供回执，晚初始化保留早到回执。破甲和中间阶段不算胜利。
3. **只补计数仍不足以开门。** 开发实测中两名客机均收到 Cough、计数为 0，却留在 `Battle Control/Start`。私人进度模式的广播隔离曾挡住 `KILL ALL ENEMIES`，导致客机没有进入拥有零计数检查的原生 `Kill Zombies` 状态。现仅在已确认假骑士最终终局时，对该玩家自己的控制器恢复经过结构验证的原生清理事件，让原生 `END → End Wait → End` 负责开门。没有向铁门发送开门事件、禁用碰撞或按血量归零解锁。

这解释了原实现遗漏的客机终局路径，但没有用户当时的逐端日志，不能断言现场恰好由哪一种时序造成。发送队列共享缺陷在交付 0.1.39 实际 DLL 上已有独立边界复现；此次游戏失败与修复结果均另存证据。
