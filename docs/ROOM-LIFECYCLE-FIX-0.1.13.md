# 0.1.13 房间同步生命周期修复

版本：HollowConnect 0.1.13 / HKMP 3.0.0-hc10。双方必须更新完整包；一键安装仍自动发现各盘 Steam 库，也可手选游戏。樱花 FRP 的 UDP 配置不变。

当前结果：生产构建 `6ddf5b3` 的 12 组同哈希静音双客户端专项全部通过；109 项自动回归、13 项安装器检查和 14 项日志门槛自检通过。三组真实镜头判定对照成立。历史单次入场冻结仍缺少来源记录，正式发布阻塞未关闭；用户要求先试玩查 bug，现单独提供 [0.1.13 试玩包](PLAYTEST-0.1.13.md)，本次打包不更新正常游戏。

## 确认的故障链

本次本机游玩日志显示：进入大黄蜂及后续房间后，登记表仍含苔藓冲锋者和它的摄像机锁；初始化这些已经销毁的对象反复抛出异常。断线重连后出现重复场景回调和重复包处理器登记。这不是仅凭静态代码猜测的 Boss 名称匹配问题。

使用原始 0.1.12 HKMP DLL、两份隔离游戏与内存角色做[失败基线](evidence/baseline-room-0.1.12.txt)：在苔藓冲锋者真实副本 FSM 中执行原生 `AudioPlayInState`，让音源先销毁，再执行死亡和原生下一房转场。旧版在 `AudioSource.Stop → ActionInState.ExitState → ForgetActions → Entity.Destroy → ClearEntities / OnSceneUnloaded` 抛出异常；一端虽然实际进入 `GG_Hornet_1`，同步登记仍停留在旧房，随后房间模拟权检查超时。该探针故意控制对象销毁顺序，不冒充完整自然游玩复现；它复现了日志中的旧房间残留和后续登记失效。

Unity 的场景事件按订阅顺序调用。旧实现把实体清理和队友登记放在不同监听器里，前者抛错会跳过后者；重连清理中再次抛错，还会跳过客户端事件和包处理器的解绑。因此双方可进入同名原生场景，但同步系统没有一起进入这场战斗，出现队友互不可见、Boss 隐形或独立战斗。

## 公共修复

- 取消 FSM 的持续动作前先移出登记表；停止协程与退出回调只执行一次。已销毁的音源不再调用 `Stop`，退出回调失败也不会阻止其他动作的取消。
- `Entity.Destroy` 可重复调用，逐项解除观察器、组件和临时对象；清理一个对象失败不会保留整个旧房间。
- 客户端用同一个入口协调房间清理、实体登记、队友回收与入场发布。每个实际场景实例只增加一次访问编号，连接已加载的场景也走这个入口。
- 连接事件和包处理器登记有生命周期守卫；断线先移除场景与玩家监听器，再独立清理各子系统。延迟到来的旧握手和超时回调须匹配当前连接。
- 同房断线时把最近同步状态交还原生对象，再移除显示副本，防止重连把已停用的原生 Boss 登记成永久隐藏。
- 后加载的非权威实体明确初始化为副本，等待权威的启停状态；扫描拒绝把已有显示副本重新登记为原生实体。
- 为原生物体和显示副本保留子物体的初始配对与稳定身份。原生 `SetParent` 把子物体脱离 Boss 后，FSM 引用仍解析到同一对物体；战斗快照带父物体身份，不再把世界坐标误作 Boss 内的局部坐标。
- 接管前将子物体的父级、位置、旋转、缩放和启停状态交还原生侧，再停用脱离层级的显示副本；清房时也回收这些副本。只在接管时启用原生的脱离子物体，避免两份碰撞或攻击控制器同时运行。
- 初始化专用的 `FindChild` 先绑定当前层级中存在的正确对象；对象已经脱离层级时，保留仍有效的引用。末尾再处理一次子物体查找，补足初始化依赖；普通网络动作的查找语义不变。
- 同房重连登记已开始运行的原生根 FSM 时，临时保留其 `RestartOnEnable` 状态，防止暂停再激活清掉变量、重走入场；恢复初始化或销毁后归还原标志。新的入场 FSM 不套用这项规则。
- 有原生刚体的实体统一补齐既有速度、重力组件，首次和接管后发布初始值，并在恢复 FSM 前还原。速度变化最多每秒发布 20 次；这项修复复用 hc10 现有消息，没有再改协议。
- 原生物体首次登记的静态身份随物体保留。同房重连不能因为它已经脱离父物体，就按新路径生成另一 ID。身份元数据没有每帧逻辑，随原生物体销毁；复制品须核对实例和场景，动态池化生成仍使用独立生命周期 ID。
- 同房重新登记还需保留本地暂停时的运动。父物体停用前记录活跃刚体，全部独立子实体初始化后恢复；原生 FSM 已经换状态则以新状态为准。显示副本和网络接管丢弃这份本地记录，继续使用权威快照。
- 日志新增房间准备与快照提交记录，包含场景、访问编号、轮次、模拟权和队友数量，便于复查两台机器的真实表现。

修复位于共享的房间、动作与连接流程，不含大黄蜂或苔藓冲锋者专属开关。战斗仍由房间权威运行原生 Boss FSM，另一端显示同步副本；普通流程的关键物品与原生死亡分支没有改成“直接删除 Boss”。这不等于已经逐个验收所有流程奖励。

## 验证与边界

最终运行结果、实际 DLL 哈希、失败探索轮次和准确覆盖范围见 [运行证据](evidence/runtime-room-0.1.13.json)。回归结果见 [自动化输出](evidence/regression-0.1.13.txt)。静态审计使用本机实际 API 程序集，SHA-256 为 `5944411BD93830369390A4B51766EE68C4AB26195B299E25A07B5E7D0E00086D`；扫描了 3578 个类型与 1854 个数据文件。静态扫描不算 Boss 验收。

测试使用隔离游戏、内存角色、真实本机 UDP/DTLS；拦截全部存档写入接口，音乐和音效保持静音。故障注入、直接额外伤害、真实骨钉碰撞和原生入口测试各自记录，不互相冒充。

| 范围 | 本次验证方式 |
|---|---|
| 音源先销毁、死亡、转房和重连 | 对同一失败基线验证旧房实体全部移除，新房模拟权、队友、Boss 与摄像机恢复 |
| 主机先入 / 客机先入、迟到快照 | 分别启动独立双客户端，检查唯一模拟权、相同实体身份、双方可见及当前血量 |
| 大黄蜂结算到温泉 | 检查权威结算驱动原生序列，另一端跟随，下一房仍能登记队友 |
| 格林、分阶段 Boss、救援、地图与传送 | 对最终 DLL 运行已有专项，具体断言以运行证据为准 |
| 两台机器樱花 FRP、全部 Boss 招式和关键奖励 | 尚需玩家实战及逐项专项，不能从本机样本推断全部通过 |

补查保留了假骑士的两次移动/阶段失败，并查明一个确定的公共缺陷：脱离层级的显示副本地形块在接管后仍参与碰撞，原生 FSM 却指向另一块停用的地形。未移交模拟权的三轮对照正常；增加“接管后的原生引用必须对应唯一活跃碰撞体”断言后，修改前构建稳定失败。本版修复稳定身份和子树接管后，最终专项还要求恢复阶段后不存在残留地形块。诊断记录见[补查证据](evidence/hierarchy-diagnostics-0.1.13.json)。早期失败均未删除；缺少完整记录的首轮不能断定其唯一原因。

迟入场断言也经过核对：假骑士露头原生只有 5 秒，迟入加载与离房淡出超过时限后，地形收回是正确行为。测试现在检查实际阶段、保留血量与自然恢复战斗，再用原生伤害触发下一次露头，而不强设 FSM。格林固定无敌靶子必须停在场内，避免被固体碰撞推出场外后原生 `AD Pos` 永久无合法落点；这项夹具修正没有改变发行 DLL 的 Boss 逻辑。

最终构建的一次主机先入测试在第二轮虫王房检查到镜头 `FROZEN`；该时刻 Boss、队友及镜头锁状态均已同步。下一次同 DLL 的两轮测试加入被动定位/模式诊断后通过，但前次冻结没有记录调用来源，因此其唯一原因仍未确认。前次失败保留，不作为通过记录，也不能据后次通过宣称入场镜头已彻底没有问题。

后续 10 轮主机先入诊断和 12 轮客机先入内存诊断均通过。每组第一轮走前五 Boss 到温泉，后续轮只反复真实入口与首房，再退房断线重连；不是重复完整一门。内存诊断不在每次镜头定位时写文件，只在失败时输出模式来源、定位协程、输入和时间缩放。UDP 关闭修复改变了生产哈希，所以前后两组各自记录，不能合并成最终构建的 22 轮验收。镜头来源仍未知，[阻塞记录](evidence/runtime-blockers-0.1.13.json)继续阻止正式发布；此次用户要求的独立试玩包保留这一未解决问题。

真实大黄蜂投针诊断又确认了三项公共根因：初始化查找清掉脱离层级的 Needle / Needle Tink 引用、同房登记的启停导致原生 FSM 重启清变量、接管空中冲刺时缺少速度快照。只保留引用仍会跌出地图，只保留状态又会停在空中；这些失败均已保留。完整修复后，主机和客机两种先入顺序各完成六次真实投针时断线重连，要求再次投针、引用有效并自然进入 Throw Recover，双端严格日志通过。它们是最终提交前的证明，不替代最终哈希整套验收。

真实尖刺碰撞专项确认原生 `DieFromHazard → PlayerDeadFromHazard → FreezeInPlace` 会短暂冻结镜头，随后自行恢复输入与镜头。统一房间检查现在只在明确危险复位状态中允许最多 15 秒恢复；无危险状态的冻结或持续冻结仍失败，不调用强制解冻。复用了同一判定的双端专项已通过。原旧样本没有记录来源，不能反推它一定是这一原因，发布阻塞仍保留。

严格日志门槛还拦出了菜单重开房的客机 UDP 关闭异常。关闭流程现在先取消接收，再等待最后发送与释放；接收失败不会产生零长度假数据，活跃连接的错误仍记录 ERROR。两项真实套接字回归有失败前后对照，完整回归 109 项通过。随后发现单次 ICMP 注入不稳定，接收失败回归改用实际套接字超时检验同一错误分支，并要求错误入日志、队列无假数据及随后正常收包，20 次重复通过；没有修改生产超时或抑制错误。见[夹具诊断](evidence/udp-error-fixture-diagnostic-0.1.13.txt)。最终 12 组已对同一生产哈希重新运行并通过。

本轮已建立本地 Git，冻结新玩法，并统一所有模式的运行时及发布后处理日志门槛。见[发布门槛](QUALITY-GATES.md)。后续模组异常、引擎 ERROR 或 `Spawn expired` 即使出现在 `.done` 之后，仍使本轮失败。

早先最终套件在客机先入的第 5 次重连拦出新的真实失败：大黄蜂停在 Thrown，飞针引用非空但飞针停用，两端给同一原生飞针算出了不同 ID。静态 ID 来自当前层级，而断线后的原生飞针与原本停用的另一端可以处于不同层级。新增“所有静态实体 ID 必须一致”断言后，修改前构建在首次同房重连即失败。随原生物体保留身份的公共修复现已通过两个最终生命周期专项；此前 3 组通过不用于新哈希，完整 12 组已另行重跑。[阻塞记录](evidence/runtime-blockers-0.1.13.json)与补查汇总保留该失败。

身份修复后的客机先入六轮通过，房主先入却在初始重连停于 A Dash。这又暴露了本地暂停丢失运动的独立路径：定向原生冲刺基线记录速度从 `(-23.5, -18.7)` 变为 `(0, 0)`，原权威先重连后仍停在同一状态，8 秒内不能自然完成。网络速度快照不足以恢复新建组件尚未收到数据的本地暂停。保存整个层级的暂停运动后，同一冲刺样本通过；最终两组生命周期检查还必须各包含真实冲刺与六轮投针重连。

最终套件再次在第一组重连被严格日志门槛拦下：真实冲刺与第一轮投针收回均完成，但客机副本首次激活触发 `iTween.RetrieveArgs / Awake` 空引用。旧引擎的定向基线稳定复现：复制正在动画中的父子物体会带入两个运行中的 iTween，而其私有参数保存在只指向原物体的全局表，副本无法取到参数。修复在未激活的复制层级上立即移除这些复制来的运行组件，不调用可能按复制 ID 误清原动画参数的 Stop，也不修改原物体。双端对照验证原动画与参数仍完整，副本首次激活无错误，随后创建的新副本动画能正常运动。这是复制生命周期的公共修复，不限于大黄蜂。

该修复独立提交为 `6ddf5b3`，未再升级 hc10 协议。定向前后对照已通过，109 项回归及最终 12 组均对同一生产构建通过；日志门槛现有 14 项自检。前次失败继续保留于补查证据，两个最终生命周期专项均包含实际父子动画复制断言。

两个最终生命周期专项随后各完成真实冲刺及六轮投针重连。格林客机先入的一次验收则发生测试夹具故障：已载入内存角色后未设已选角色连接标志，异步选档菜单与场景切换重叠，原生 UI 出错并崩溃，随后双方超时。额外基线记录 `Hkmp.Ui.UiManager.GoToSaveMenu` 在 Town 再次调用 ProfileMenu。纠正相关游戏内探针后，假骑士两组及格林两个先入顺序重新通过；生产 DLL 不变，之前受影响夹具的通过不复用。菜单新档专项仍保留真正选档路径。日志检查增至 10 项自检，原生崩溃与访问冲突也直接判失败；不能据这次夹具故障解释玩家历史掉线。

旧版已经分叉的运行状态不能通过在运行中覆盖 DLL 修复。更新时关闭游戏；所有玩家升级后重新开房并重新进入挑战。

最终镜头门槛另以三组真实 Unity 对照验证：无危险状态的冻结立即失败；真实尖刺触发原生冻结后，在测试进程中阻塞 `PlayerDeadFromHazard` 恢复协程，两端均在 15 秒后失败；正常尖刺复位则自行恢复。早先停止时间倍率的注入被游戏恢复，未形成预期故障，已单独保留失败。两组预期拒绝不算战斗通过，也没有强制镜头解冻。[镜头对照](evidence/camera-gate-0.1.13.json)补足判定证明，不能倒推历史单次冻结的唯一原因。

## 两台机器复测顺序

以下流程使用按用户要求提供并核验的 0.1.13 试玩包；未解决问题继续保留，不视为正式发布验收完成。

1. 双方完整安装 0.1.13，重启游戏，核对 HKMP 为 `3.0.0-hc10`。重新开房，再开始新的一门挑战。
2. 第一轮房主先入、队友晚入；第二轮反过来。迟入时重点观察队友、Boss 与镜头，分别对 Boss 挥刀并确认另一端血量同步。
3. 连续进入大黄蜂并击杀；双方应由同一次权威结算进入温泉。中途暂时分处相邻房间可以存在，已进入同房后不应继续各自战斗。
4. 正常退出挑战、退菜单并重连，重复上述入场顺序。无需用 F8 掩盖可见性或房间登记问题。
5. 若复发，双方分别保留当次 `ModLog.txt`，重点比较 `Room prepared` 和 `Room snapshot committed` 的场景、访问编号、轮次与模拟权；两人的访问编号可不同，同房同轮应恰有一个模拟权威。原始日志可能含玩家名称和地址，发行包不收录事故原日志。
