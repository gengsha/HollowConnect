# 0.1.13 房间同步生命周期修复

版本：HollowConnect 0.1.13 / HKMP 3.0.0-hc10。双方必须更新完整包；一键安装仍自动发现各盘 Steam 库，也可手选游戏。樱花 FRP 的 UDP 配置不变。

## 确认的故障链

本次本机游玩日志显示：进入大黄蜂及后续房间后，登记表仍含苔藓冲锋者和它的摄像机锁；初始化这些已经销毁的对象反复抛出异常。断线重连后出现重复场景回调和重复包处理器登记。这不是仅凭静态代码猜测的 Boss 名称匹配问题。

使用原始 0.1.12 HKMP DLL、两份隔离游戏与内存角色做[失败基线](evidence/baseline-room-0.1.12.txt)：在苔藓冲锋者真实副本 FSM 中执行原生 `AudioPlayInState`，让音源先销毁，再执行死亡和原生下一房转场。旧版在 `AudioSource.Stop → ActionInState.ExitState → ForgetActions → Entity.Destroy → ClearEntities / OnSceneUnloaded` 抛出异常；一端虽然实际进入 `GG_Hornet_1`，同步登记仍停留在旧房，随后房间模拟权检查超时。该探针故意控制对象销毁顺序，不冒充完整自然游玩复现；它复现了日志中的旧房间残留和后续登记失效。

Unity 的场景事件按订阅顺序调用。旧实现把实体清理和队友登记放在不同监听器里，前者抛错会跳过后者；重连清理中再次抛错，还会跳过客户端事件和包处理器的解绑。因此双方可进入同名原生场景，但同步系统没有一起进入这场战斗，出现队友互不可见、Boss 隐形或独立战斗。

## 公共修复

- 取消 FSM 的持续动作前先移出登记表；停止协程与退出回调只执行一次。已销毁的音源不再调用 `Stop`，退出回调失败也不会阻止其他动作的取消。
- `Entity.Destroy` 可重复调用，逐项解除观察器、组件和临时对象；清理一个对象失败不会保留整个旧房间。
- 客户端用同一个入口协调房间清理、实体登记、队友回收与入场发布。每个实际场景实例只增加一次访问编号，连接已加载的场景也走这个入口。
- 连接事件和包处理器登记有生命周期守卫；断线先移除场景与玩家监听器，再独立清理各子系统。延迟到来的旧握手和超时回调须匹配当前连接。
- 同房断线时把最近同步状态交还原生对象，再移除显示副本，防止重连把已停用的原生 Boss 登记成永久隐藏。
- 后加载的非权威实体明确初始化为副本，等待权威的启停状态；扫描拒绝把已有显示副本重新登记为原生实体。
- 为原生物体和显示副本保留子物体的初始配对与稳定身份。原生 `SetParent` 把子物体脱离 Boss 后，FSM 引用仍解析到同一对物体；战斗快照带父物体身份，不再把世界坐标误作 Boss 内的局部坐标。
- 接管前将子物体的父级、位置、旋转、缩放和启停状态交还原生侧，再停用脱离层级的显示副本；清房时也回收这些副本。只在接管时启用原生的脱离子物体，避免两份碰撞或攻击控制器同时运行。
- 日志新增房间准备与快照提交记录，包含场景、访问编号、轮次、模拟权和队友数量，便于复查两台机器的真实表现。

修复位于共享的房间、动作与连接流程，不含大黄蜂或苔藓冲锋者专属开关。战斗仍由房间权威运行原生 Boss FSM，另一端显示同步副本；普通流程的关键物品与原生死亡分支没有改成“直接删除 Boss”。这不等于已经逐个验收所有流程奖励。

## 验证与边界

最终运行结果、实际 DLL 哈希、失败探索轮次和准确覆盖范围见 [运行证据](evidence/runtime-room-0.1.13.json)。回归结果见 [自动化输出](evidence/regression-0.1.13.txt)。静态审计使用本机实际 API 程序集，SHA-256 为 `5944411BD93830369390A4B51766EE68C4AB26195B299E25A07B5E7D0E00086D`；扫描了 3578 个类型与 1854 个数据文件。静态扫描不算 Boss 验收。

测试使用隔离游戏、内存角色、真实本机 UDP/DTLS；拦截全部存档写入接口，音乐和音效保持静音。故障注入、直接额外伤害、真实骨钉碰撞和原生入口测试各自记录，不互相冒充。

| 范围 | 本次验证方式 |
|---|---|
| 音源先销毁、死亡、转房和重连 | 对同一失败基线验证旧房实体全部移除，新房模拟权、队友、Boss 与摄像机恢复 |
| 主机先入 / 客机先入、迟到快照 | 分别启动独立双客户端，检查唯一模拟权、相同实体身份、双方可见及当前血量 |
| 大黄蜂结算到温泉 | 检查权威结算驱动原生序列，另一端跟随，下一房仍能登记队友 |
| 格林、分阶段 Boss、救援、地图与传送 | 对最终 DLL 运行已有专项，具体断言以运行证据为准 |
| 两台机器樱花 FRP、全部 Boss 招式和关键奖励 | 尚需玩家实战及逐项专项，不能从本机样本推断全部通过 |

补查保留了假骑士的两次移动/阶段失败，并查明一个确定的公共缺陷：脱离层级的显示副本地形块在接管后仍参与碰撞，原生 FSM 却指向另一块停用的地形。未移交模拟权的三轮对照正常；增加“接管后的原生引用必须对应唯一活跃碰撞体”断言后，修改前构建稳定失败。本版修复稳定身份和子树接管后，最终专项还要求恢复阶段后不存在残留地形块。诊断记录见[补查证据](evidence/hierarchy-diagnostics-0.1.13.json)。早期失败均未删除；缺少完整记录的首轮不能断定其唯一原因。

旧版已经分叉的运行状态不能通过在运行中覆盖 DLL 修复。更新时关闭游戏；所有玩家升级后重新开房并重新进入挑战。

## 两台机器复测顺序

1. 双方完整安装 0.1.13，重启游戏，核对 HKMP 为 `3.0.0-hc10`。重新开房，再开始新的一门挑战。
2. 第一轮房主先入、队友晚入；第二轮反过来。迟入时重点观察队友、Boss 与镜头，分别对 Boss 挥刀并确认另一端血量同步。
3. 连续进入大黄蜂并击杀；双方应由同一次权威结算进入温泉。中途暂时分处相邻房间可以存在，已进入同房后不应继续各自战斗。
4. 正常退出挑战、退菜单并重连，重复上述入场顺序。无需用 F8 掩盖可见性或房间登记问题。
5. 若复发，双方分别保留当次 `ModLog.txt`，重点比较 `Room prepared` 和 `Room snapshot committed` 的场景、访问编号、轮次与模拟权；两人的访问编号可不同，同房同轮应恰有一个模拟权威。原始日志可能含玩家名称和地址，发行包不收录事故原日志。
