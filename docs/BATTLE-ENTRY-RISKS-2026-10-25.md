# 战斗入口修复：三项定向风险验证

本轮复用黑波前灵魂战士入口修复的生产 DLL，仅新增任务专用诊断夹具；没有继续修改生产源码。用户要求时间紧、只做必要验证，因此未扩大完整矩阵。复用的 8 项核心检查与原 3 组入口实测见 `docs/BATTLE-ENTRY-FIX-2026-10-25.md`，以相同生产哈希为前提。

| 风险 | 原生实测边界 |
|---|---|
| 先入场者尚未进入中央就结束战斗 | `Ruins1_31b` 中负责敌人的玩家停在 x40，队友触发开战；原生健康伤害结束 Boss 后，双方完成结算并开门；该玩家随后进入中央，门保持打开，镜头没有延迟锁定。 |
| 开战后负责敌人的客户端断线 | 真实 UDP 客户端断开，保留服务器；另一端接管原 Boss ID 和受损血量，没有重生第二只 Boss；Folly 继续移动且被真实骨钉碰撞击杀；原玩家重连返回后，双方完成原生结算并开门。 |
| 没有常规计数器的特殊战斗控制器 | `White_Palace_20` 的原生控制器没有 `Battle Enemies`；新入口适配器排除两只 Kingsmould。击杀第一只不能提前完成，两只都死亡后双方封门碰撞关闭，两名角色实际走过封门。 |

第三项验证的是一个真实且被新逻辑排除的特殊控制器，不等于证明所有可能接受入口适配的无计数器 Boss 都安全。当前 `LocalBattleStart.Find` 不要求计数器存在，而延迟门/镜头逻辑会在计数器缺失时取消待执行动作；本轮没有发现一个实际满足其余适配条件的原生无计数器 Boss 场景，故此抽象结构边界仍不能宣称已由实机覆盖。

三组串行使用原有 `game-host` / `game-guest` 隔离副本，使用未保存的新角色，共享永久进度开启。Boss 和守卫的结尾使用原生 `HealthManager.ApplyExtraDamage` 伤害边界；这验证原生死亡和结束流程，不代表全程人工战斗。未验证三客户端、异机或 FRP 网络。

用例清单、逐项状态、双端日志、严格日志检查、夹具哈希、原生依赖及清理记录在 `.analysis/battle-entry-risks-20261025/`。机器可读最终结果为 `docs/evidence/battle-entry-risks-2026-10-25.json`。只有该结果文件标为 `passed` 且双方完成、严格日志与生产哈希均匹配的用例才算通过。
