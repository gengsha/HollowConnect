# 联机修复的发布门槛

本轮冻结玩法，只处理房间分叉、对象生命周期和验证缺口。Git 从当前工作状态建立本地基线；它不能补出旧版本的可靠开发历史。旧安装包仍保留，事故日志、玩家存档、游戏程序集及隔离运行目录不纳入 Git 或发行包。后续每项修复独立提交，提交说明记录失败证据与验证范围。

## 日志也是失败条件

所有隔离运行模式通过同一个 `ProbeLogGuard` 记录引擎 ERROR、模组异常和 `Spawn expired`，包含网络线程与 Unity 多行堆栈；立即写入失败标记。发布汇总还扫描每轮全部 `.log`，包括独立的引擎日志。`.done` 或 `FINAL PASS` 不能覆盖稍后出现的 `.failed`。原生 `Crash!!!`、崩溃处理器及 Access Violation 标记也直接失败。原版 UI 警告和诊断中的原生状态名 `Stun Fail` 不一概判失败，也没有宽泛忽略模组异常的白名单。十四项日志门槛自检覆盖这些区别。异常堆栈逐行检查，保留最多后续 35 行和空行/新时间戳边界，避免在超长 Unity 日志上反复回溯；边界有明确正反断言。

每轮核对实际三项生产 DLL 哈希、双方完整终态、失败标记及日志门槛。改代码、Git 构建标识或构建参数造成 DLL 变化时，旧哈希的通过不能算作新构建验收。失败探索、夹具修正和正式验收分开记录；重跑通过不删除前次失败。

新门槛在菜单重开房专项拦出一次真实关闭窗口：已收到服务器 Shutdown 后，`NetClient.Disconnect` 仍先等待更新器发送最后一包，UDP 接收线程此时尚未取消，Windows 可报告 ConnectionReset。现在先取消接收，再保留发送端完成最后一包并释放连接；活跃连接的套接字错误仍记 ERROR。失败接收不再入队零长度假数据。两个真实套接字回归在修改前失败、修改后通过，完整自动回归为 109 项；基线见 `evidence/socket-shutdown-baseline-0.1.13.txt`。本项未改传输格式或升级 hc10 协议号。

单次 ICMP 注入后来出现未触发预期接收错误的失败，不能通过忽略该断言放行。最终回归改用真实套接字接收超时覆盖同一错误分支，仍必须记录实际错误、错误后队列为空、下一有效包完整且可取消。失败、重试注入未奏效和替代刺激的覆盖限制见[夹具诊断](evidence/udp-error-fixture-diagnostic-0.1.13.txt)。生产接收没有增加超时或降低日志级别。

## 清理与初始化的语义

动态生命周期结束应发送退役记录，回收显示对象并从活跃实体表剔除；静态 Boss 死亡仍保留房间内的网络死亡记录，用来阻止迟入和旧消息使其复活。房间切换先分离整张活跃表，再逐项释放动作、组件及脱离父层级的对象。针对已销毁 Unity 对象的守卫不能用来掩盖初始化 ERROR。

`Entity.InitializeHost` 在 `SetActive` 前设定模拟权，是为了让同步接管中的原生激活/入场事件可以执行。它不代表全部组件已成功初始化；简单移回旧位置可能阻断这些事件。现有清理故障已有原始 DLL 的受控失败基线和修复验证。将初始化时序列为审查点是合理的，但不能只凭赋值顺序就断言它是格林或此次分叉的已证实根因。

已直接读取两份历史源码 ZIP 核对：0.1.7 的确定标志在 `SetActive` 之后，0.1.9 提前到其前方，并新增入场事件重放；用户指出的顺序变化属实。对应 ZIP SHA-256 分别为 `BC2C639628AF6EF464165C7ED938824DF18373F196FE198942E740FD7CDA8453` 与 `36EAF8A46737BB9893EBB34FB9D7D244E0976F84484C3506FFD589A311851B0F`。当前代码在入口拒绝已销毁实体和失效 Unity 主对象；这些对象不能再次执行 `SetActive`。全部组件成功就绪与已获得模拟权仍是不同状态，不据旧旗标赋值推断初始化完成。

## 验收与更新

用户明确要求先打包试玩时，可用 `Package.ps1 -Playtest` 和 `Verify-Release.ps1 -Playtest` 制作、核验独立试玩包。其请求及允许的未解决问题保存在 `evidence/playtest-authorization-0.1.13.json`，并绑定本次已验收 DLL 的哈希。试玩包仍要求 12 组完整运行记录、严格日志和一致的生产哈希；manifest 标记 `playtest`、保留已知问题和 `releaseReady=false`。普通发布仍拒绝未解决问题，不把试玩请求改写为问题已解决。此次请求只打包，正常游戏未自动安装。

本机静音双客户端用于验证可重复的生命周期、状态和传输不变量；真实两台机器、完整 Boss 招式、普通流程关键奖励仍各自验收。固定无敌测试角色必须保持场内位置；格林的场外固定靶子可能令原生 AD Pos 永远重试，不能把这类零样本测试计为通过。

游戏内探针已经载入内存角色，连接时必须使用已选角色路径，不能又启动异步选档菜单。一次客机先入格林因遗漏标志重开原生 ProfileMenu，发生 UI 错误、原生崩溃及随后超时；实际菜单调用基线已保留。修正的是测试夹具，不据此断言玩家历史掉线原因。专门检验从菜单选档/新档的 JoinProbe 仍走原生选档路径。

镜头的瞬时 `FROZEN` 需要记录来源。真实尖刺危险复位会进入该状态；统一房间判定只在 `hazardDeath / hazardRespawning` 为真时允许最多 15 秒等待原生恢复输入与镜头，其他冻结仍失败，不强制解冻。已知原生短暂冻结的证明，不能倒推没有调用记录的旧失败一定来自同一路径。

镜头判定另有三组真实 Unity 对照：无危险状态冻结立即拒绝，真实尖刺碰撞后阻塞原生复位协程在 15 秒后拒绝，正常尖刺复位自行恢复。预期失败只属于门槛对照，不计战斗验收；停止时间倍率却被原生代码恢复的旧夹具失败也独立保留。[对照证据](evidence/camera-gate-0.1.13.json)不关闭历史来源未知的发布阻塞。

对照使用同一日志扫描器，只允许两个明确注入场景的精确失败原因。双方必须都留下相应失败标记、不能有完成标记，其他模组异常及运行错误仍拒绝；自检包含“预期失败不能掩盖另一模组异常”。正常验收与发布脚本不传这个测试参数。

一键安装器执行覆盖更新，自动发现 Steam 库或接受手选目录，不要求卸载、搬动游戏或重配隧道。已加载 DLL 需要退出重启；协议改动要求双方兼容，纯本地修复应避免无必要的协议升级。本轮子物体父级快照改变了传输格式，因此双方需要同版引擎。后续不把每次本地修复自动当作协议升级。

EasyTier、Tailscale、直连端口转发和樱花 FRP 都是网络路径选择，无法修复对象清理抛错、重复监听或房间登记失效。先用可复现证据修复模组，再在用户实际网络上验证；没有证据支持把更换隧道作为本次修复的前提。
