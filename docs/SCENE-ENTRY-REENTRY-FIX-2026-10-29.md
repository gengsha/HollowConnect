# 联机入场期间的重复过门请求

用户提供的 0.2.3 视频中，角色进入苍绿之径一代大黄蜂房后出现开场对白，随后平台房与大黄蜂房交替闪现并反复黑屏。本次修复转场入口的一条可导致同类异常的重入路径：在线时，已接受的入场尚未完成，出口碰撞不能再次发起加载。

## 已确认的边界缺陷

原生 `TransitionPoint.OnTriggerEnter2D` 主要检查碰撞层和 `GameManager.gameState == PLAYING`，没有检查原生加载是否仍在进行、角色是否已经就位。`PauseManager` 以前直接执行解除暂停和原生过门逻辑。

真实入场时，角色会先放在目标入口的出口触发区内。0.2.3 双端检查记录到：`Fungus1_04/right1` 的中心为 `(95.5,33)`，角色在同处，`IsInSceneTransition=true`、`isHeroInPosition=false`、`cState.transitioning=true`。在这个实际物理碰撞回调中受控地提前恢复 `PLAYING`，两端都接受了第二次加载请求，目标是 `Fungus1_21/left1`。

探针在加载入口捕获并抑制了第二个请求，保留第一个原生入场完成。这证明了入口重入漏洞；没有把受控条件写成已自然复现整段视频。视频是他人录制，是否按 F8、存档和第三方模组配置未知。0.2.3 的“队友先触发开场、另一人正常从邻房进入”和真实 F8 两条自然对照在本机都没有出现持续循环。

## 修改

`src/HKMP/Game/Client/PauseManager.cs` 在执行暂停恢复、淡出和原生过门动作之前，在线检查 `IsInSceneTransition` 和本机角色就位状态。原生加载仍在进行，或角色不存在／尚未就位时，直接忽略本次回调。就位后的正常过门与暂停中正常出房仍走既有逻辑。离线分支沿用原逻辑。

没有添加推测性的队友身体过滤，也没有修改 Boss FSM、开战／击败标记、协议、共享进度或存档。最早的“队友身体经过出口会带走本机”假设未通过物理接触前提，已在调查记录中排除。

## 验证与证据

生产源码基于当前 0.2.4 工作树，保留其已有修复，没有升版、打包或安装。增量生产构建通过；出现一项既有的 `ClientUpdateManager.AddEntityHostFsmData` XML 参数注释警告。Smoke 构建与 6 项选定核心检查通过（6/6）。
