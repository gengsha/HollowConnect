# 0.2.4 剧情首领战门禁收尾修复（2026-10-29）

玩家反馈格鲁兹之母、收藏家和守望者骑士团死亡后仍被关在战场。截图只展示倒地的骑士与关闭的门，无法确定当时是否已击败全部六只、是否掉线重连以及进度共享设置。本次以发布的 0.2.4 原始 DLL 建立基线，再修复实际复现的路径；不把所有反馈归结为一个已经证明的原因。

## 已确认的缺口

### 收藏家在队友离线期间完成收尾

原版 0.2.4 的 `boss-gates-20261029-024-collector-reconnect-c` 中，两端正常进场并关门，非权威端断线，权威端通过原生伤害与处决击打完成死亡流程。权威端进入 `Death/Send Event`、本地 `Battle Scene/End`，两扇门开启。另一端在原场景重连后仍可操作，`collectorDefeated=true`，但首领已不再注册，本地控制器仍在 `Start`，两扇门持续 `Close 2`；额外等待十二秒也不恢复。

旧实现把最终 FSM 快照排队等待已消失的首领实例，无法把已确认的 `BATTLE END` 交给本地战斗控制器。

修复在首领仍存在时记录原生 FSM 中经过击败记录验证的终态位置。该记录只包含场景实例与状态结构，断线后保留，原生场景卸载时删除。只有当前访问、当前轮次且来自重新入场快照的对应终态，才可在对象缺失时恢复本地原生结束事件。普通动态对象、未知结构、伤残/处决未完成状态及生命值为零均不能触发此路径。关闭共享时，也只恢复该终态原生前置链中已有白名单允许的正向击败布尔标记；不复制奖励、图鉴计数或任意进度字段。未修改网络包格式。

### 死亡先到、战斗绑定后到

原版 `boss-gates-20261029-024-late-binding-a` 的显式接收边界检查失败：敌人尚未绑定本地控制器时收到终局死亡，随后到达的死亡前 Health 元数据被丢弃，本地剩余敌人数无法收到这次死亡。

修复只让当前生命周期的迟到元数据补上已挂起的本地计数回执，不更新死亡实体的血量、无敌、阶段或存活状态；重复元数据不重复扣减，旧生命周期的元数据不能污染重置后的新死亡。该证据是受控接收顺序检查，不代表已自然复现用户现场网络顺序。

### 格鲁兹之母关闭进度共享时的开战分歧

原版 `boss-gates-20261029-024-mother-private-b` 中，真实非致命骨钉碰撞唤醒权威端，但队友本地 `Battle Control` 收不到 `START`。逐步追踪还确认：仅放行 START 不足以恢复完整流程，过滤器会拦截空 `Music` 状态的即时 `FINISHED` 以及本地关门事件。

修复只识别 `Crossroads_04` 中格鲁兹之母对原生 `Battle Scene/Battle Control` 的 START，核对 `Music → Start`、七只幼虫计数和 BATTLE START 动作。让这个本地控制器运行自己的原生后续动作，再恢复外层远端广播过滤。门在战斗中仍保持实体阻挡，清完真实幼虫后才开门。该问题是已确认的开战不同步，不能单独当作用户“战后不开门”现场的证明。

## 验证范围

原始发布版的正常路径：格鲁兹之母共享模式、收藏家共享/私有模式、六只守望者骑士完整战斗均通过。守望者原生结尾有五秒与两秒等待，之后才有开门动画；本次不会据单只骑士死亡或生命值归零强行开门。

最终固定 DLL 的验收记录见 `.analysis/boss-gates-20261029/final-run.json`、`final-progress.json` 和最终 `final-results.json`。最终用例清单为 `final2-preflight.json` 与 `final2-selection.json`，共九组串行双端检查：

| 接收顺序边界及原生蘑菇巨怪战斗 | 迟到绑定、重复、旧生命周期元数据、死亡不可逆与真实门禁收尾 |

全部实机检查使用既有隔离副本、同机真实 UDP、临时未保存角色与存档保护。未修改个人存档。历史失败与早期构建的记录均保留，最终验收只认对应 DLL 哈希；没有双机外网认证，也没有宣称覆盖所有首领或用户现场的所有触发条件。

本任务未升版本、打包、安装、提交或发布。此前的场景入口重入和竞技场边界修复仍保留在工作区，未被本次覆盖。
